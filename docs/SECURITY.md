# Security boundaries and integration notes

This is a small, trusted-team hackathon starter. The demo is protected, but it is not a multi-user authentication system. Add real identities, authorization, per-user job ownership, rate limiting and audit policy before making it a public user application.

## Included controls

- Only Caddy publishes ports 80/443. PostgreSQL, Redis, FastAPI and Caddy's health listener have no public host mappings. Oracle ingress remains an independent requirement.
- Same-origin relative `/api` requests avoid a permissive CORS policy. HTTPS is automatic for the configured DuckDNS hostname; local mode intentionally uses loopback HTTP.
- Job submission, status and system information require a constant-time Bearer-key check. Health/readiness expose only coarse status. API docs are disabled on the server.
- The demo form holds the admin key in memory, never browser persistent storage. The key is not bundled into frontend assets. Any teammate with that key can submit and inspect all jobs; it is not suitable for end users.
- Caddy applies a 16 KB body limit, anti-framing and content-type headers, and a same-origin content security policy. The API validates demo input length at 4,000 characters. Invalid signed webhook requests are rejected before work is enqueued.
- API/worker/migration containers run as UID 10001 with a read-only root filesystem, temporary `/tmp`, dropped capabilities and no-new-privileges. Data services and Caddy use their official image defaults.
- Redis has a generated password, AOF and noeviction. RQ uses JSON serialization in both API and worker, avoiding pickle payloads. Redis still must remain private; do not let arbitrary clients create RQ jobs.
- SQL values are parameterized. Migration execution is serialized by an advisory transaction lock. Secrets are runtime-only and excluded from Git/Docker build contexts.
- GitHub Actions have read-only repository token permissions, pinned action commits, no production secrets on PR checks, verified SSH hosts, a dedicated key and a deployment lock. Only `main` can deploy; the production job is gated by `DEPLOY_ENABLED`.

## Understand the remaining trust

The deploy account belongs to Docker's root-equivalent group. A person able to modify deployed repository code or use the deployment SSH key can control the VM. The `restrict` SSH-key option disables forwarding/PTY, not command execution or Docker access. Limit repository writers and keep the key exclusive to this project. Rotate it if exposed. Native server-side builds execute code from `main`, so review dependency and Dockerfile changes from contributors.

Runtime environment variables are visible to a host administrator and Docker operators. A private `.env` is appropriate for this trusted-team start; a longer-lived system can move to mounted secrets or a secret manager. Do not expose `docker inspect` or full resolved Compose output publicly. The environment parser assumes plain unquoted `KEY=value` lines generated by the configuration tool; do not source `.env` as shell code.

No automatic authentication provider, distributed rate limiter, queue quota, abuse protection, database row retention, metrics/alerts, outbox dispatcher, high availability or encrypted offsite backup is configured. Public `/api/ready` proves dependencies are available, not that a worker is alive. A real completed-job check supplies that evidence. The UI polls for one minute; jobs can continue after it stops polling.

The starter uses the database owner account for both migrations and application queries. Separate a restricted application role from the migration role before a longer-lived deployment, and avoid storing sensitive production data until the access model and retention policy are defined.

RQ cannot guarantee exactly-once effects. A worker crash or lost enqueue response can leave an uncertain job. The sample records an explicit `enqueue_failed` state and returns 503 with `X-Job-ID`; check that ID before retrying. PostgreSQL retains finished results after Redis's one-day result expiry. Hard job failures are reconciled when status is requested while RQ failure metadata still exists; a catastrophic Redis loss can leave stale queued/running DB rows. Recovery requires deliberate review. Redis AOF and Docker volumes are not a substitute for off-machine backups.

## Connect a messenger or external service

`/webhooks/demo` is a working **example protocol**, not a Telegram/WhatsApp/Slack implementation. It accepts JSON `{"text":"hello"}` with:

```text
X-Webhook-Timestamp: Unix seconds
X-Webhook-Signature: hex HMAC-SHA256(WEBHOOK_SECRET, timestamp + '.' + exact raw JSON bytes)
```

Requests outside a five-minute timestamp window fail. The handler bounds body size, verifies the raw body, enqueues quickly and returns 202. Replaying the same valid request within that window creates another job: **event deduplication is not implemented**. Add a provider event-ID table with a unique constraint and a transactional outbox before processing retries from a real messenger. The demo's uppercase task is deterministic and harmless to repeat.

Follow the chosen messenger's official verification procedure. Some providers use a shared-secret header instead of this HMAC; others have a GET challenge or need a specific response deadline. Use a separate provider credential, verify signatures before parsing, deduplicate event IDs, acknowledge promptly, and do slow/external calls in RQ. Do not accept arbitrary callback URLs or function names from a webhook. Set network timeouts, response-size limits and retry/idempotency rules for every outbound service. Keep upstream credentials only in backend/worker configuration. No paid external service is called or subscribed to by this repository.

## A deployment is not zero-downtime

Compose replaces containers on one host; traffic can pause and a long job can delay replacement until the grace period ends. New SQL migrations may run while the old application is still serving requests, so keep schema changes backward compatible. App rollback does not reverse migrations. A VM/disk outage affects every service. When the application becomes important, adopt tested restore procedures, independent backups and a suitable availability plan.
